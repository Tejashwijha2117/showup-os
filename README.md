# SHOWUP OS | Phase 4
Attendance Growth Intelligence for RISA Labs' fictional CampusFest. Bengaluru, Challenge A. Phase 4 standalone application; no live hosting or LLM integration yet.

## Run
1. Extract ZIP. Open terminal in the extracted `showup-os` directory.
2. Use Python 3.10+; optionally create a virtual environment: `python -m venv .venv` (activate using `.venv\Scripts\activate` on Windows or `source .venv/bin/activate` on macOS/Linux).
3. `python -m pip install -r requirements.txt`
4. `python app.py`
5. Open http://127.0.0.1:8000. Interactive API docs: http://127.0.0.1:8000/docs.
6. Run `python test_app.py` (tests use isolated copies and do not change the original demo DB). To reset planning data, extract a fresh copy of showup.db. Do not run import on the working DB unless intentionally refreshing historical tables.

## Product brief
Primary user: festival growth PM. Secondary: two campus leads, digital lead, lifecycle lead, operations/analytics lead. JTBD: When targets are at risk, identify the bottleneck, evaluate options within time/budget/capacity, assign an accountable action, then monitor outcomes. Value: optimize verified attendance rather than registration vanity metrics. Measure → diagnose → decide → execute → monitor → reallocate.

## Architecture
Browser (HTML/CSS/JS, Tailwind CDN, Chart.js CDN) → FastAPI JSON endpoints → shared engine.py → SQLite. Historical raw and deduplicated tables are imported from RISA workbook; planning tables and synthetic outcomes are separate. Every dashboard refresh requests server calculations. Phase 5 copilot should use the same read endpoints and confirmed task-write endpoint, not duplicate arithmetic. No secret or external account is necessary for Phase 4. Use server-side secret storage for future LLM API keys. Local server binds to loopback by default. Optional reviewer authentication is enabled by setting SHOWUP_PASSWORD. The application is a single shared demo workspace, not a multi-tenant production system.

## Files
- `app.py`: API, validation, persistent writes and audit trail.
- `engine.py`: historical snapshot, forecast, decision rules.
- `schema.sql`: exact SQLite planning schema; source schema generated by importer.
- `import_data.py`: reads every original workbook sheet, preserves raw rows, checks conflicting IDs and removes only repeated identical IDs in cleaned tables. Original Excel is included separately in the archive as `Attendee Dataset.xlsx`.
- `showup.db`: preimported, ready-to-run database.
- `index.html`: five application screens and a context-only AI drawer.
- `test_app.py`, `TEST_RESULTS.txt`: API regression tests and recorded results.
- `render.yaml`: free web service blueprint; health check and required start command.

## Metric definitions
All historical timestamps are local wall time in Asia/Kolkata. Date filters mean end of day. Targets use most recent effective version. Latest registration history per registration_id uses effective_at, history_id order; a person with any confirmed registration is counted once as confirmed. Historical person filters use external type, first_seen_at and first_campaign_id. Registration count = distinct eligible person IDs with a registration by selected date. Attendance = distinct external person IDs, admitted AND verified, timestamp between event start and min(event end, selected cutoff). Registered attendees = intersection of registered and attendance IDs; walk-ins = attendees minus registered. CPA = net posted spend / registered attendees; blended = spend / all unique attendees; CPR = spend / registered people; zero denominator = null. Reported reach is summed, not globally unique. Campaign attribution is first-touch association, not incremental causality. Final identified count includes 125 walk-ins; pre-event cohort conversion uses April 11, not April 20 denominator. Historical targets are global even with campaign filter.

## Locked planning inputs
Historical 2050; paid reduction ₹30,000; retained allocation ₹246,500; five bets ₹53,500 (pilot ₹12,000 / conditional ₹41,500), six people × 10h × 12 weeks = 720h, 205 bet hours, 515 other hours including contingency. Base 2420, downside 2190, stretch 2600. Base contributions (Assurance, Referrals, Campus, Recovery, Waitlist) = [100,100,192,60,20]. Stretch [150,140,250,85,27]; downside [50,60,120,30,10]. Loss 102 base/stretch; 130 downside. All assumptions are unvalidated. Modelled capacity = floor(min(daily unique limit, 85% concurrent occupancy × 10 operating hours / (dwell × 1.5 peak multiplier), gate throughput × peak arrival window / peak arrival share) / busiest-day share), default 2714. This is not a safety certification. Forecast is capped at capacity and flagged if raw demand exceeds it. Budget/team violations are flagged, not automatically optimized. Changing budget ceiling does not magically reduce committed budgets; reduce allocations explicitly. Changes to bet funding/hours/time scale impact linearly up to locked plan; not a causal forecast. For minimum pilot sample, leading signal caps contribution using locked proxy conversion assumptions; this is a deliberately conservative sensitivity, not measured lift. New custom campaigns need independent overlap-adjusted contribution estimates. All projected values are modelled, not actual attendance.

## Decision rules
Use minimum pilot samples (400 people, 100 referrers, 5 campuses, 150 leads, 20 offers). Scale only if leading signal and projected incremental CPA meet thresholds and manual guardrail is pass. Budget/team/capacity violation blocks SCALE. STOP if guardrail fails or observed signal/CPA crosses stop threshold. Otherwise TEST/CHANGE. See engine.py for exact thresholds. Operator enters measured leading signals and sample; raw pilot treatment-control records and statistical analysis are future enhancements. For a scale decision, confirm actual evidence and safe available slots; manual guardrail defaults to pass as a planning placeholder, not verified evidence. Completing a task never creates attendance. Synthetic verified outcome records are unique by synthetic person ID across campaigns, separate from original history; they are demo records, not a complete new festival attendance ledger.

## Demo script
1. Overview: historical 2050, forecast 2420 / 2600. Funnel intelligence: select Apr 11, confirm zero attendance and ₹276,500 spend; select Mar 14 vs Mar 15 to see budget revision.
2. Campaigns: edit Campus Cohort Commitments, set signal 8 and sample 5. Save. Base forecast drops to 2356 and campus projected CPA rises to ₹171.9; STOP appears. This is the modeled pilot scenario, not historical evidence.
3. Execution: create task for campus lead to diagnose activation drop, choose deadline and completion criteria. Save and refresh; mark Done and confirm actual attendance did not change.
4. Campaigns: add synthetic outcome SIM-001 twice. Count remains one.
5. Scenario lab: change peak share to 0.8; stretch capped at 2375. Preview updates automatically; save a named snapshot or explicitly apply the inputs to the live plan. Reduce budget to 225000 to surface infeasible allocation, then edit budgets deliberately.

## Experiments and scenarios
Experiments have a unique campaign foreign key, hypothesis, method, metric, minimum sample, status, signal, sample and guardrail. Changes to pilot observations are synchronized transactionally with campaign fields consumed by the shared engine. Each custom campaign gets an experiment record. No causal uplift is inferred automatically. Scenario snapshots store complete settings and campaign inputs separately from the live plan. `/api/preview` computes without writing, `/api/scenarios` saves a named immutable snapshot, `/api/scenarios/{id}` recomputes it, `/api/plan` explicitly applies preview inputs. Scenario conversion and show-up rates are 0–1 sensitivity inputs referenced to 0.80 and 0.6875; conversion affects campus/referral/recovery/custom bets, show-up affects all incremental bets. These are simplified relative sensitivities, not a reconstructed future person-level funnel; extreme rate settings should not be treated as validated effects. Scenario budget and retained allocations are separately editable; check budget alerts and reconcile paid reductions manually. `verified_external_admissions` is the cleaned eligibility view; raw source tables are kept separately and not writable via application APIs.

## Deploy to Render
1. Extract the archive and push the contents of `showup-os/` to your GitHub repository root (including the pre-populated `showup.db`).
2. In Render create a Blueprint from that repository, or a Python web service with these commands:
   - Build: `pip install -r requirements.txt`
   - Start: `uvicorn app:app --host 0.0.0.0 --port $PORT`
   - Health: `/health`
   - Instance: Free
3. Set an optional `SHOWUP_PASSWORD` environment variable to a strong unique password before sharing a public demo. Login is `reviewer`; share the password privately with the evaluator if necessary. No password is bundled. Health checks remain public. This is a simple shared reviewer gate, not role-based access control.
4. Open the Render URL and run the browser checklist below. The package is configured for deployment; actual cloud deployment has not been performed.

**Important:** Render free web service filesystems are ephemeral. The bundled SQLite database initializes the demo but edits are lost on restart, redeploy or spin-down. Local edits persist on disk. For durable hosted SQLite use a paid persistent disk and set `SHOWUP_DB` to a path on that disk, e.g. `/var/data/showup.db` (the seed database is copied on first boot). See https://render.com/docs/free and https://render.com/docs/disks. The free configuration is a review/demo deployment, not a durable production datastore. CDN connectivity is required for Tailwind/Chart.js; fallback styles and historical trend tables remain available if scripts fail.

## Scope and limitations
No real LLM, no fabricated responses, no notification delivery, no automatic experimental inference, no role-level authorization or multi-user isolation. Simulated outcome records do not automatically update the forecast; this avoids treating incomplete demo attendance as causal campaign lift. Historical figures are synthetic RISA assignment data, not real events. Planning capacity is an assumption and not a safety certification. The UI uses Tailwind utilities plus a local CSS fallback. Deployment and browser end-to-end verification remain outstanding; the automated backend suite does not certify browser rendering or external services.
